# Распознавание дорожных знаков и светофора

Задача из техзадания № 2: робот должен распознавать знаки **«Стоп»**,
**«Пешеходный переход»**, **«Искусственная неровность»**, сигналы светофора и
препятствия. В этом репозитории распознавание работает на всех четырёх камерах
Logitech C930e (спереди слева/справа, сзади слева/справа), показывает рамки на
кадрах, ставит отметки знаков **на поле карты** и определяет
**красный / жёлтый / зелёный**.

> Важно: модуль формирует факты для навигации, а **не команды тяге**.
> `action: stop|slow|signal|avoid` и `trafficLight.action` — рекомендации;
> остановку перед стоп-линией по-прежнему решает `road_traffic.py` и контроллер
> маршрута. Так E-STOP и существующие блокировки остаются единственным
> источником команд моторам.

## Классы

Порядок фиксирован — он же порядок `names` в `data.yaml` и `model.names`:

| id | класс | подпись | цвет рамки | действие |
| --- | --- | --- | --- | --- |
| 0 | `stop_sign` | Знак «Стоп» | `#ff3d71` | `stop` |
| 1 | `pedestrian_crossing` | Пешеходный переход | `#2f9bff` | `slow` |
| 2 | `speed_bump` | Искусственная неровность | `#ffb020` | `slow` |
| 3 | `traffic_light` | Светофор | `#a78bfa` | `signal` |
| 4 | `cone` | Конус / столбик | `#ff7a29` | `avoid` |

Конусы на поле карты ПДД не наносятся (это препятствия для лидара), но в кадре
подсвечиваются и попадают в `counts`.

## Откуда данные

Репозиторий [`p25543770-lang/yolo-stop`](https://github.com/p25543770-lang/yolo-stop)
содержит архив `yolo-20261117T081703Z-1-001.zip` с 54 фотографиями полигона и
**без файлов разметки**. Поэтому:

1. `scripts/vision_dataset.py` скачивает архив с `codeload.github.com`
   (или берёт `--zip`), раскладывает кадры по `images/train` и `images/val`
   (детерминированно, 80/20 по хэшу имени);
2. размечает их `HeuristicDetector` — теми же правилами, что работают на роботе
   без PyTorch. Синий знак выпрямляется перспективно и классифицируется по
   чёрному символу в белом треугольнике; СТОП — пурпурный восьмиугольник;
   светофор — сетка ярких диодов на тёмном корпусе;
3. пишет `labels/*.txt` (`cls cx cy w h`, координаты 0…1), `data.yaml`,
   `dataset.json` (количества, SHA-256 архива) и `annotations.json` (рамки +
   цвет сигнала для каждого кадра).

Сами JPEG **не коммитятся** (`.gitignore`): ~6.8 МБ скачиваются заново. Метки,
`data.yaml` и манифест лежат в Git, поэтому обучение воспроизводимо.

```bash
python scripts/vision_dataset.py                         # скачать + разметить
python scripts/vision_dataset.py --zip ~/Downloads/yolo-....zip
python scripts/vision_dataset.py --no-download           # переразметить без сети
```

## Обучение

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements-vision.txt
# ultralytics тянет opencv-python с libGL; на безголовом роботе:
.venv/bin/pip uninstall -y opencv-python
.venv/bin/pip install "opencv-python-headless<5"

.venv/bin/python scripts/train_vision.py --epochs 150 --imgsz 416 --batch 4
.venv/bin/python scripts/train_vision.py --smoke --from-scratch   # 2 эпохи → yolo-stop-smoke.pt, metadata-smoke.json
```

* Если доступны COCO-веса `yolov8n.pt`, скрипт дообучает их (качество выше).
  Порог по умолчанию `RC_VISION_CONF=0.45` отсекает ложные `STOP 0.38` на
  баннерах, не теряя основные рамки.
  Если интернета нет — строит `yolov8n.yaml` **с нуля**; на узком наборе из
  пяти классов это рабочий вариант, но для финала желательна машина с GPU.
* Результат — `models/vision/yolo-stop.pt` и `metadata.json` (метрики,
  версия ultralytics, состав датасета). Логи/графики — в `runs/vision/`
  (в Git не попадают).
* После перезапуска киоска `/api/vision/state` покажет
  `backend: "yolo+heuristic"`. Веса можно заменить вручную:
  `RC_VISION_MODEL=/path/to/best.pt`.
* Метрики обученной модели: precision 0.51, recall 0.74, **mAP50 0.770**,
  mAP50-95 0.595 на 13 валидационных кадрах (150 эпох, CPU, с нуля).

## Два источника детекций

* **YOLO** (`YoloDetector`) — если `models/vision/yolo-stop.pt` существует и
  установлен `ultralytics`. `model.names` приводится к нашим именам, включая
  русские алиасы.
* **Встроенный детектор** (`HeuristicDetector`) — если весов/PyTorch нет.
  Работает на OpenCV: HSV-маски, контуры, перспективное выпрямление синего
  знака, склейка диодов светофора вертикальным ядром. Он же используется для
  авторазметки, поэтому «резерв» и обучающая выборка не расходятся.

Когда доступны оба, работает `EnsembleDetector`: рамки YOLO имеют приоритет
при пересечении, а находки эвристики (конусы, не попавшие в обучающую выборку
секции табло) добавляются после NMS. Оба возвращают
`Detection(cls, box, confidence, color, color_counts)`; `box` — нормированные
`x, y, w, h`, так что размер кадра не важен.

## Светофор: красный / жёлтый / зелёный

`classify_traffic_light()` считает яркие насыщенные пиксели внутри рамки:

| сигнал | тон OpenCV | действие |
| --- | --- | --- |
| красный | 0…12, 173…179 | `stop` |
| жёлтый / оранжевый | 13…38 | `prepare` |
| зелёный | 39…88 | `go` |

Пурпурный баннер (155…170) и синий LED-экран (90…130) в диапазоны не попадают,
зелёная стена отсекается порогом яркости диодов. `TrafficLightTracker`
голосует по последним 7 кадрам, переключает цвет только после двух кадров
большинства и забывает состояние через `RC_VISION_TRAFFIC_STALE_S` секунд.
В `trafficLight.counts` приходят **все три** цвета одновременно: на панели
лампы подсвечиваются пропорционально числу диодов, а текущим считается
доминирующий. Для реальной езды `RC_VISION_PREFER_RED=1` заставляет любой
заметный красный сигнал перебивать остальные.

## Отметки на поле

Для каждой рамки (кроме конусов) сервис оценивает пеленг и дальность:

```
bearing = yaw_камеры + (0.5 − x_central) · HFOV
distance = height_класса · f_px / (h_рамки · высота_кадра)
f_px = (ширина_кадра / 2) / tan(HFOV / 2)
x = x_камеры + d·cos(bearing),  y = y_камеры + d·sin(bearing)
```

`yaw`, положение камеры и `hfov_deg` берутся из `sensor_layout.camera_specs()`
(переменные `RC_CAMERA_*` в `.env`). Это **грубая оценка по угловому размеру**:
для точных координат нужны замеренная геометрия и/или глубина Kinect. Пока
`GET /api/sensors/layout` сообщает `calibrated=false`, относительное
расположение отметок на поле следует считать ориентировочным.

На странице камер мини-поле рисует робота внизу по центру и знаки вперёд/по
бокам; на `/map` (`map_view.js`) те же отметки переворачиваются в мировые
координаты по курсу робота из `api/kiosk_map`.

## 3D-знаки в «Общем обзоре · 3D» Kinect

На вкладке **«Общий обзор · 3D»** (`robot.html`, `index.html`, `scan.html`)
поверх облака Kinect/лидара и модели робота рисуются найденные знаки как
**объёмные таблички в масштабе 1:1**: STOP — красный восьмиугольник, синие
знаки — квадрат с белым треугольником, светофор — тёмное табло с тремя лампами
и подсвеченным текущим сигналом. Тонкая стойка показывает проекцию знака на пол,
а сетка сцены размечена в метрах, так что 30-сантиметровый STOP занимает ровно
0,3 м относительно корпуса робота.

* Размеры берутся из `robot_control/vision/classes.py`: `width_m`, `height_m`,
  `thickness_m`, `shape`, `center_height_m`. Это типовые размеры учебных
  макетов; для настоящего 1:1 замерьте свои знаки и поправьте константы или
  `RC_VISION_SIGN_SCALE` в `.env`.
* `VisionService` добавляет в каждый маркер `z_m` (высота центра над полом),
  `zSource` (`camera-geometry` или типовой `CLASS_INFO` при неоткалиброванной
  высоте камеры), `headingDeg`, `width_m`, `height_m`, `thickness_m`, `shape`,
  `sizeScale`, `positionSource`.
* `kinect_view.js` переводит `(x_m, y_m, z_m)` из системы карты (X вперёд,
  Y влево) в систему 3D-вида `[X_вправо, Y_вверх, Z_вперёд] = [-y_m, z_m, x_m]`
  и ориентирует табличку нормалью к роботу. Данные приходят через
  `rc-vision-state` / `RCVision.onState`, новый метод —
  `RCKinectView.setVisionMarkers(field)`.
* Положение пока **оценка по угловому размеру с C930e**, а не измерение
  глубиной Kinect: `positionSource: "camera-estimate"`. Облако Kinect даёт
  общий 3D-контекст, но не уточняет координаты знака. Для привязки к глубине
  нужна калибровка связки «камера ↔ Kinect» и отдельный проектор луча в кадр
  глубины.
* Знаки рисуются только при свежем `/api/vision/state` (около 1,5 с) и только
  в совмещённом режиме; при выключенном распознавании 3D-обзор остаётся прежним.

## API

| Метод | Путь | Что отдаёт |
| --- | --- | --- |
| GET | `/api/vision/state` | `backend`, `cameras` (рамки), `counts`, `trafficLight`, `field`, `classes`, `inferenceMs` |
| GET | `/api/vision/field` | только отметки поля + светофор (для карты) |
| GET | `/api/vision/camera/<0…3>/frame` | JPEG с нарисованными рамками (404, если кадра нет) |
| POST | `/api/vision/camera/<0…3>/frame` | принять JPEG от внешнего источника и сразу разметить |
| POST | `/api/vision/config` | `{"enabled": bool, "confidence": 0…1}` |
| GET | `/api/vision/classes` | справочник классов и подписей сигналов |

Маршруты зарегистрированы и в веб-пульте (8080, с авторизацией и CSRF для
POST), и в бортовом киоске (8090). В режиме `master-peer` пульт проксирует
состояние и размеченные кадры с борта, не открывая свои USB-камеры.

## Панель четырёх камер

* `slam_gui/main.html` (инженерный пульт) и `slam_gui/robot.html` (киоск):
  блок `#vision-panel` с тремя лампами, списком найденных знаков, мини-полем и
  переключателем «рамки на кадрах».
* `camera_frames.js` и `camera_view.js` при включённой разметке запрашивают
  `/api/vision/camera/<id>/frame` вместо обычного `/api/camera/<id>/frame`.
  Рамки рисует **сервер на том же JPEG**, поэтому цифровой зум, отражение и
  панорама (`camera_stitch.js`) не сдвигают их относительно изображения.
* `map.html` подключает только `vision_panel.js`: он опрашивает
  `/api/vision/state` и событием `rc-vision-state` передаёт отметки в
  `map_view.js`.

## Переменные `.env`

См. блок `RC_VISION_*` в `.env.example`: `RC_VISION_ENABLED`,

## Ограничения

1. Датасет узкий: 54 кадра одного помещения, метки сгенерированы эвристикой.
   Для соревнования желательно доснять знаки с разных расстояний/углов и
   разметить их вручную (например, в Roboflow/CVAT), затем повторить обучение.
2. Цвет светофора определяется по **доминирующему** цвету диодов. Если табло
   одновременно показывает все три секции (как на нескольких учебных фото),
   текущим будет самый яркий/многочисленный; `counts` при этом содержит все три.
3. Проекция знаков на поле и в 3D — оценка по высоте рамки и геометрии C930e,
   не измерение дальности Kinect. Не используйте её как единственный источник
   для торможения. Масштаб 1:1 честный ровно настолько, насколько совпадают
   физические размеры в `CLASS_INFO` с макетами на полигоне.
4. Сервис не включает тягу и не снимает E-STOP. Интеграция с навигацией —
   следующий шаг: `road_traffic.py` уже умеет стоп-линии и циклы светофора,
   к нему можно подвести `trafficLight.state` вместо симуляции по времени.
5. На 2-ядерном CPU обучение с нуля занимает десятки минут; на GPU — минуты.
   Встроенный детектор работает без PyTorch и без весов, но уступает YOLO в
   устойчивости к ракурсам и частичным перекрытиям.
6. Глубина Kinect пока не уточняет координаты знаков: 3D-обзор показывает
   `positionSource: "camera-estimate"`. Для метровой привязки к облаку точек
   нужна совместная калибровка камер и Kinect.
