# Распознавание дорожных знаков и светофора

Робот распознаёт **«Стоп»**, **знак искусственной неровности**, пешеходный
переход, светофор (красный / жёлтый / зелёный / выключенный или неоднозначный)
и оранжево-белые оградительные столбики, объединённые в класс `cone`.
**Физическая кочка на полу — другая задача:** для неё нужны данные рельефа и
`ground_hazards.py`, а не рамка знака `speed_bump`.

Сервис работает с четырьмя камерами, рисует рамки и отметки поля/3D. Он
**не посылает команды моторам**, не снимает E-STOP и не подменяет торможение
по лидару/глубине. `action` — факт/рекомендация для навигации.

## Веса-кандидат и протокол

**Цветовая часть кандидата пока ненадёжна; для автономной езды не готова.**

- **[YOLO по съёмкам с Google Диска](VISION_DRIVE.md)** — отдельный офлайн-детектор `models/vision/yolo-drive.pt`.
  В отличие от бортовой модели рисует рамку **самой кочки** (`ground_bump`) отдельно от знака (`speed_bump`).
  Это не измерение высоты по Kinect и не команда на проезд.
- `models/vision/yolo-stop.pt` — прежние рабочие 5-классовые веса, сохранены.
- `models/vision/yolo-stop-candidate.pt` — исходный 8-классовый кандидат (baseline), сохранён.
- `models/vision/yolo-stop-improved.pt` — предыдущий отдельный стендовой кандидат.
  Прирост, ухудшения и выбранный фильтр корпуса — в **[VISION_IMPROVEMENT.md](VISION_IMPROVEMENT.md)**.
- `models/vision/yolo-stop-robot.pt` / `.onnx` — результат следующего полного
  дообучения: 34 фактические эпохи, best 14, проверенный FP32-экспорт.
  **Формальный VAL-допуск не пройден; только офлайн/изолированный стенд.**
  Метрики, конфликт старой VAL-метки, регрессии и все проверки — в
  **[VISION_ROBOT_TRAINING.md](VISION_ROBOT_TRAINING.md)**. Production не заменён.
- `models/vision/yolo-stop-candidate.json` — SHA-256 весов, база, параметры,
  фактически выполненные эпохи, отдельные val/test и метрики по классам.
- **[VISION_TRAINING.md](VISION_TRAINING.md)** — результаты выполненного
  обучения, ограничения, включение на роботе. Числа из старой валидации на
  13 фотографиях не являются оценкой новой модели.

## Закрытый полигон: неизвестный сигнал и 5 секунд

Дополнительный режим **выключен по умолчанию**:
`RC_VISION_CLOSED_COURSE_TIMEOUT=1`. После 5 секунд новых свежих unknown-кадров
того же корпуса возвращает отдельное `trafficLight.closedCourse.recommendation`.
**Цвет остаётся unknown, `action` остаётся wait, тяга не включается.**
Red/yellow блокируют эту рекомендацию, а потеря/устаревание кадров отменяет
ожидание. Это не исправление ненадёжных цветов кандидата и не допуск к езде.
Условия, API, отображение и ограничения —
**[VISION_CLOSED_COURSE.md](VISION_CLOSED_COURSE.md)**.

## Классы: совместимость API и обучения

`CLASS_NAMES` — неизменный публичный контракт из пяти классов. Расширенный
`TRAINING_CLASS_NAMES` сохраняет первые пять id и добавляет сигналы:

| id YOLO | класс модели | результат в API | назначение |
| --- | --- | --- | --- |
| 0 | `stop_sign` | `stop_sign` | знак «Стоп» |
| 1 | `pedestrian_crossing` | `pedestrian_crossing` | переход |
| 2 | `speed_bump` | `speed_bump` | **знак** неровности |
| 3 | `traffic_light` | `traffic_light`, `signal=unknown` | off / несколько сигналов / неоднозначность |
| 4 | `cone` | `cone` | конус / оградительный столбик |
| 5 | `traffic_light_red` | `traffic_light`, `signal=red` | красный |
| 6 | `traffic_light_yellow` | `traffic_light`, `signal=yellow` | жёлтый |
| 7 | `traffic_light_green` | `traffic_light`, `signal=green` | зелёный, требуется подтверждение HSV |

Синий/красный цвет рамки в API не равен цвету сигнала: последний передаётся
полем `signal`. Светофор размечается **по корпусу**, не одной горящей линзе.
Одновременные red+green и выключенные табло не размечаются как разрешающий
зелёный. Конусы в кадре подсвечиваются и считаются, но на карту знаков ПДД
не наносятся — это препятствия, а не таблички.

## Откуда данные и как воспроизвести

Источник: [`p25543770-lang/yolo-stop`](https://github.com/p25543770-lang/yolo-stop),
commit `3cb277bfadf7d0034943117f9146d4b92bb773a9`. На этой версии 415 JPEG,
вложенный ZIP со старыми 54 фото и 8 MP4; готовой YOLO-разметки нет.

**Основа уже выполненного обучения — данные именно этого репозитория.**
[Проверка происхождения, SHA и цепочки обучения](VISION_SOURCE.md).
Для восстановления поставленного датасета **без изменения меток/разбиения**:

```bash
.venv/bin/python scripts/restore_vision_source.py --restore-missing
```

Команда проверяет закреплённый архив, все 373 JPEG и 8 MP4, добавляет только
отсутствующие файлы и отказывает при конфликте SHA. Это не повторное обучение
и не переразметка. Подробности и холодная проверка восстановления — в отчёте.

Отдельно `scripts/vision_dataset.py` создаёт **новый** набор (пересоздаёт
предложения/метки/группы, не использовать вместо восстановления):

1. читает **все** фото, вложенные ZIP и видео (а не только старый ZIP);
2. извлекает видео примерно с частотой 1 кадр/с и удаляет точные дубликаты
   по SHA-256: остаются **308 фото + 65 видеокадров = 373**, удалены 107 копий;
3. строит предложения рамок `scripts/vision_bootstrap.py`; файл
   `reviewed_annotations.json` заменяет их для 214 изображений. Поставляемые
   исправления визуально сделаны агентом, часть рамок приблизительная;
   это **не независимая ручная ground-truth-разметка**;
4. объединяет все кадры одного видео и близкие pHash (расстояние ≤8) в
   транзитивные группы. Делит группами, со стратификацией: **260 train,
   61 val, 52 test**, все восемь классов есть в каждой части;
5. сохраняет `labels/{train,val,test}/*.txt`, `data.yaml`, `dataset.json`,
   `annotations.json`, `samples.json` (источник/время/хэш/группа/часть) и
   `duplicates.json` (какая копия исключена).

Хэш и commit исходника проверяются; у произвольного локального `--zip`
не приписывается чужой commit. Тяжёлые JPEG, MP4, ZIP и кэши не хранятся в Git.

```bash
python scripts/vision_dataset.py                         # закреплённый источник
python scripts/vision_dataset.py --zip source-repo.zip   # или свой архив
python scripts/vision_dataset.py --no-download           # использовать кэш
python scripts/vision_dataset.py --no-download --annotations reviewed.json
```

Формат исправлений: `{имя_кадра: [{"class": "stop_sign", "box": [x,y,w,h]}]}`,
координаты нормированы 0…1; для светофора добавляется `"signal": "red"`
(`yellow`, `green`, `unknown`). Можно указать `class=traffic_light_green`.
Пустой список означает проверенный фон и **не** перезаписывается эвристикой.

**Важно:** pHash убирает известные пересечения групп, но не гарантирует
независимость ракурсов одного помещения. Тест на этих псевдометках измеряет
согласие с разметкой, а не безопасность движения в новом месте.

## Обучение

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements-vision-training.txt
# Ultralytics также тянет GUI opencv-python; для headless Linux:
.venv/bin/pip uninstall -y opencv-python
.venv/bin/pip install --force-reinstall --no-deps opencv-python-headless==4.11.0.86

# Обычная машина с доступом к официальным COCO-весам и CUDA:
.venv/bin/python scripts/train_vision.py --weights yolov8n.pt --device 0 --epochs 150 --imgsz 640 --batch 16

# Если GitHub release assets недоступен, только codeload (как в этой среде):
.venv/bin/python scripts/fetch_vision_weights.py
.venv/bin/python scripts/train_vision.py --weights .cache/vision/pretrained/coco-repacked.pt --device cpu --epochs 40 --imgsz 416 --batch 8 --freeze 10 --patience 15 --cache disk

# Проверка пайплайна: отдельные *-smoke.pt/json, не рабочая модель:
.venv/bin/python scripts/train_vision.py --smoke --from-scratch --imgsz 320 --batch 2
```

- По умолчанию результат — **candidate**, не рабочий файл. Без `--weights`
  используется warm start от имеющегося `yolo-stop.pt`; это не COCO и не
  обучение с нуля. `--from-scratch` явно выбирает случайную инициализацию,
  никогда не берёт локальные веса и не служит молчаливым fallback.
- До старта проверяются все метки, ненулевые рамки, диапазоны id/координат,
  SHA-дубликаты и пересечения групп между частями. Сохраняется переносимый
  fingerprint содержимого; изменение датасета во время обучения отменяет
  публикацию модели.
- Device `auto` выбирает CUDA при наличии, иначе CPU. Доступны `--workers`,
  `--seed`, `--patience`, `--freeze`, `--lr0`, `--cache`, `--data`, `--output`,
  `--onnx`. Для второго этапа можно разморозить все слои: `--freeze 0 --lr0 0.0002`.
- Hue shift и отражения отключены: нельзя превращать красный в зелёный или
  зеркалить слово STOP. Яркость/небольшой поворот/масштаб/перспектива остаются;
  mosaic выключается в последних десяти эпохах.
- Каждый запуск имеет отдельную папку `runs/vision/<UTC-id>/`. Лучшая модель
  выбирается **только по val**, затем `best.pt` отдельно проверяется на
  val и test. В JSON — фактические эпохи из CSV, не только запрошенное число.
  Для промежуточных экспериментов/этапов используйте `--validation-only`,
  чтобы не смотреть test до окончательного выбора весов и параметров по val.
- `--resume runs/vision/<id>/train/weights/last.pt` продолжает незавершённый
  запуск при неизменном fingerprint и наличии `dataset-audit.json`. Для
  нового дообучения от готового best используйте `--weights`, не `--resume`.
- `--deploy` — явное разрешение записать в `models/vision/yolo-stop.pt`;
  `--smoke --deploy` и случайная запись smoke в рабочий файл запрещены.
- Предобученные веса и Ultralytics имеют собственные условия лицензирования;
  см. [Ultralytics LICENSE](https://github.com/ultralytics/ultralytics/blob/main/LICENSE).
  Скрипт загрузки фиксирует зеркало, revision и SHA содержимого, а не исполняет
  код стороннего репозитория. Это закреплённое стороннее зеркало: его хэш
  **не сверён независимо** с хэшем официального релизного файла.

После выбора весов по val можно отдельно проверить рабочий порог и
консервативную fusion-логику, включая число ошибочных green относительно
имеющихся меток (это не гарантия безопасности):

Пример воспроизведения **стендовой** конфигурации из отчёта (не для тяги):

```bash
.venv/bin/python scripts/evaluate_vision.py --confidence .25 --imgsz 512 --no-prefer-red --preview docs/vision-candidate-preview.jpg
# Также проверить именно ансамбль, как в стандартном сервисе:
.venv/bin/python scripts/evaluate_vision.py --ensemble --confidence .25 --imgsz 512 --no-prefer-red --output models/vision/yolo-stop-candidate-ensemble.json
# Подбор до test: --calibrate использует исключительно val.
.venv/bin/python scripts/evaluate_vision.py --calibrate --imgsz 512 --output .cache/vision/calibration/summary.json
```

Скрипт не подбирает порог на test; в JSON сохраняет TP/FP/FN, матрицу цвета,
предсказания **для каждого** кадра, хэш весов и fingerprint. Иллюстрации
выбираются по классам/порядку файлов, не по успешности детекций.

## Два источника детекций

`YoloDetector` нормализует имена классов модели в публичные пять классов и
сохраняет цветовую голову в `signal`. `RC_VISION_IMGSZ=416` и
`RC_VISION_DEVICE=cpu` задают размер входа/устройство; увеличение до 640 стоит
проверить на FPS и пропусках маленьких знаков именно на бортовом компьютере.
`HeuristicDetector` остаётся резервом без PyTorch.

`EnsembleDetector` отдаёт приоритет пересекающимся рамкам YOLO. При цветовой
YOLO-модели дополнительный green от одной эвристики переводится в unknown,
иначе резерв обходил бы проверку согласия. Все рамки — нормированные x,y,w,h.

## Светофор и защита от ложного green

HSV считает насыщенные светящиеся пиксели: red 0…12/173…179, yellow 13…38,
green 39…88. Малое число пикселей или существенная смесь цветов → unknown.
`RC_VISION_PREFER_RED=1` даёт красному приоритет и внутри ROI, и между камерами.

Для цветовой YOLO-модели **green требует одновременно YOLO=green и HSV=green**.
Конфликт/темнота/generic не разрешают движение, red/yellow консервативно
перебивают green. Старые пяти-классовые веса по-прежнему используют HSV для
цвета. Отключение YOLO оставляет эвристику — это не эквивалент цветовой модели.

`TrafficLightTracker` сглаживает мерцание окном из 7 кадров и гистерезисом.
Голоса старше `RC_VISION_TRAFFIC_STALE_S` исключаются, а новые unknown-кадры
**не освежают старый green**. Повторное использование кадра другой камеры
не добавляет голос и не обновляет время свидетельства. Конфликтующие
пересекающиеся рамки цветовых классов не выбираются в пользу green только
из-за большей confidence. При `RC_VISION_PREFER_RED=1` свежий red прерывает
накопленные green-голоса без ожидания большинства.

Поле `trafficLight.action=go` по-прежнему не является командой тяге и не
означает, что можно отключить другие датчики.

## Ограничения движения по знакам (`RC_GUARD_*`)

**По умолчанию выключены** (`RC_GUARD_ENABLED=0`): знаки, светофор и конусы
только распознаются и показываются. Движение целиком подконтрольно клавиатуре —
ни один класс детекции не снимает и не ограничивает тягу, и борт даже не
подключает ограничитель к `KeyboardControl`. В этом состоянии поля
`state()["guard"]` и `data.driveGuard` честно сообщают `enabled: false` и
причину, панель камер ничего не блокирует, а в режиме «Скан» и автономности
никаких проверок знаков нет.

При `RC_GUARD_ENABLED=1` из наблюдений выводятся два правила, которые **борт**
применяет к управлению с клавиатуры (WASD):

1. **Красный светофор.** Красный, подтверждённый `RC_GUARD_RED_FRAMES` кадрами
   подряд (**2 по умолчанию**) с одной и той же камеры, запрещает выдачу тяги.
   Один кадр не блокирует: одиночные вспышки, отражения и чужие красные
   предметы попадают в кадр регулярно. Серия считается по **сырым кадрам**, а
   не по сглаженному `TrafficLightTracker` (тот уже голосует окном из 7 кадров).
   Блокировка снимается только **подтверждённым зелёным**
   (`RC_GUARD_GREEN_FRAMES`, тоже 2) или явным `release`; «красный пропал из
   кадра», устаревание и таймаут её **не снимают**. Жёлтый не блокирует сам и
   не снимает уже подтверждённый красный.
2. **Знак «искусственная неровность» (кочка).** Пока `speed_bump` есть в
   свежих кадрах (и `RC_GUARD_BUMP_HOLD_S` секунд после него, чтобы робот успел
   доехать), потолок тяги WASD снижается на `RC_GUARD_SLOWDOWN` (**20 %** по
   умолчанию). Автономные режимы это не затрагивает: у них свои пределы.

Проверка стоит в `KeyboardControl` перед каждой командой тяги (`arm`, `live`,
`drive`), поэтому устаревшая вкладка, повторный запрос или удержание клавиши её
не обходят. Отказ возвращается как `409` с `reason: "red_light_block"`; руль,
`stop` и `end` работают всегда — стоящий робот должен уметь тормозить и
готовиться к проезду. Сессия WASD при этом **не закрывается**: оператор ждёт
зелёный в той же сессии. Сломанный ограничитель считается блокировкой
(fail-closed). Без сервиса распознавания (нет камер, `RC_VISION_ENABLED=0`,
стенд) ограничений нет.

Состояние видно в `state()["guard"]` (и дублируется в
`trafficLight.guard`), в `/api/kiosk_state` как `data.driveGuard`, в ответе
`begin` как `guard` и на панели камер («ТЯГА ЗАБЛОКИРОВАНА»). Это индикация и
решение борта, а не команда моторам: E-STOP, препятствия и разрешение
навигации проверяются отдельно.

Переменные: `RC_GUARD_ENABLED`, `RC_GUARD_RED_FRAMES`, `RC_GUARD_GREEN_FRAMES`,
`RC_GUARD_SLOWDOWN`, `RC_GUARD_BUMP_HOLD_S`, `RC_GUARD_STALE_S`, а также
`RC_GUARD_RED_BLOCK=0` / `RC_GUARD_BUMP_SLOW=0` для раздельного отключения.

### Опциональные фильтры корпуса и секции (стенд)

`RC_VISION_TRAFFIC_MODE=body` фильтрует рамки по геометрии вертикального
тёмного корпуса (отношение высоты к ширине 1.6…5.5, минимум 40% тёмных
пикселей). Фильтр применяется **ПОСЛЕ NMS**: может только удалить рамку,
но не перекрасить её, добавить green или восстановить green, подавленный
конфликтующим red/unknown. Для цветовой модели правило **YOLO-green И
HSV-green** остаётся неизменным. Backend сервиса — `yolo+body`.

Более строгий `RC_VISION_TRAFFIC_MODE=verified` дополнительно требует
светящиеся пиксели в соответствующей секции: red сверху, yellow посередине,
green снизу. В нём dark/unknown не заменяется догадкой цветовой головы, а
пяти-классовая модель не может выдать green. Этот эксперимент **не выбран
итоговым**: на val потерял слишком много правильных сигналов.

Оба фильтра — эвристики для вертикальных макетов с полигона, **не
универсальная проверка светофора**. Возможны пропуски маленьких, наклонённых,
светлых и частично закрытых головок. Они не доказывают, что объект — светофор.

- В режимах `body`/`verified` эвристический ансамбль не используется. Если
  модель отсутствует/не загружается или режим написан с ошибкой,
  backend=`unavailable`, а не резервный детектор без этих проверок.
- `RC_VISION_HEURISTIC=0` отдельно отключает дополнительные эвристические
  рамки **и** fallback без весов даже в `legacy`. По умолчанию этот флаг = 1.
- `trafficMode`, `heuristicEnabled` и backend видны в `/api/vision/state`.
  В `evaluate_vision.py` применяются те же `--traffic-mode body|verified`.
- По умолчанию остаётся `legacy`; рабочий файл весов и конфигурация робота
  автоматически не заменяются. Замеры, регрессии и стендовой профиль —
  **[VISION_IMPROVEMENT.md](VISION_IMPROVEMENT.md)**.

## Отметки на поле

Для каждой рамки (кроме конусов) сервис оценивает пеленг и дальность:

```
bearing = yaw_камеры + (0.5 − x_central) · HFOV
distance = height_класса · f_px / (h_рамки · высота_кадра)
f_px = (ширина_кадра / 2) / tan(HFOV / 2)
x = x_камеры + d·cos(bearing),  y = y_камеры + d·sin(bearing)
```

`yaw`, положение камеры и `hfov_deg` берутся из `sensor_layout.camera_specs()`
(переменные `RC_CAMERA_*` в `.env`). Это **грубая оценка по угловому размеру**:
для точных координат нужны замеренная геометрия и/или глубина Kinect. Пока
`GET /api/sensors/layout` сообщает `calibrated=false`, относительное
расположение отметок на поле следует считать ориентировочным.

На странице камер мини-поле рисует робота внизу по центру и знаки вперёд/по
бокам; на `/map` (`map_view.js`) те же отметки переворачиваются в мировые
координаты по курсу робота из `api/kiosk_map`.

## 3D-знаки в «Общем обзоре · 3D» Kinect

На вкладке **«Общий обзор · 3D»** (`robot.html`, `index.html`, `scan.html`)
поверх облака Kinect/лидара и модели робота рисуются найденные знаки как
**объёмные таблички в масштабе 1:1**: STOP — красный восьмиугольник, синие
знаки — квадрат с белым треугольником, светофор — тёмное табло с тремя лампами
и подсвеченным текущим сигналом. Тонкая стойка показывает проекцию знака на пол,
а сетка сцены размечена в метрах, так что 30-сантиметровый STOP занимает ровно
0,3 м относительно корпуса робота.

* Размеры берутся из `robot_control/vision/classes.py`: `width_m`, `height_m`,
  `thickness_m`, `shape`, `center_height_m`. Это типовые размеры учебных
  макетов; для настоящего 1:1 замерьте свои знаки и поправьте константы или
  `RC_VISION_SIGN_SCALE` в `.env`.
* `VisionService` добавляет в каждый маркер `z_m` (высота центра над полом),
  `zSource` (`camera-geometry` или типовой `CLASS_INFO` при неоткалиброванной
  высоте камеры), `headingDeg`, `width_m`, `height_m`, `thickness_m`, `shape`,
  `sizeScale`, `positionSource`.
* `kinect_view.js` переводит `(x_m, y_m, z_m)` из системы карты (X вперёд,
  Y влево) в систему 3D-вида `[X_вправо, Y_вверх, Z_вперёд] = [-y_m, z_m, x_m]`
  и ориентирует табличку нормалью к роботу. Данные приходят через
  `rc-vision-state` / `RCVision.onState`, новый метод —
  `RCKinectView.setVisionMarkers(field)`.
* Положение пока **оценка по угловому размеру с C930e**, а не измерение
  глубиной Kinect: `positionSource: "camera-estimate"`. Облако Kinect даёт
  общий 3D-контекст, но не уточняет координаты знака. Для привязки к глубине
  нужна калибровка связки «камера ↔ Kinect» и отдельный проектор луча в кадр
  глубины.
* Знаки рисуются только при свежем `/api/vision/state` (около 1,5 с) и только
  в совмещённом режиме; при выключенном распознавании 3D-обзор остаётся прежним.

## API

| Метод | Путь | Что отдаёт |
| --- | --- | --- |
| GET | `/api/vision/state` | `backend`, `cameras` (рамки), `counts`, `trafficLight`, `field`, `classes`, `inferenceMs` |
| GET | `/api/vision/field` | только отметки поля + светофор (для карты) |
| GET | `/api/vision/camera/<0…3>/frame` | JPEG с нарисованными рамками (404, если кадра нет) |
| POST | `/api/vision/camera/<0…3>/frame` | принять JPEG от внешнего источника и сразу разметить |
| POST | `/api/vision/config` | `{"enabled": bool, "confidence": 0…1}` |
| GET | `/api/vision/classes` | справочник классов и подписей сигналов |

Маршруты зарегистрированы и в веб-пульте (8080, с авторизацией и CSRF для
POST), и в бортовом киоске (8090). В режиме `master-peer` пульт проксирует
состояние и размеченные кадры с борта, не открывая свои USB-камеры.

## Панель четырёх камер

* `slam_gui/main.html` (инженерный пульт) и `slam_gui/robot.html` (киоск):
  блок `#vision-panel` с тремя лампами, списком найденных знаков, мини-полем и
  переключателем «рамки на кадрах».
* `camera_frames.js` и `camera_view.js` при включённой разметке запрашивают
  `/api/vision/camera/<id>/frame` вместо обычного `/api/camera/<id>/frame`.
  Рамки рисует **сервер на том же JPEG**, поэтому цифровой зум, отражение и
  панорама (`camera_stitch.js`) не сдвигают их относительно изображения.
* `map.html` подключает только `vision_panel.js`: он опрашивает
  `/api/vision/state` и событием `rc-vision-state` передаёт отметки в
  `map_view.js`.

## Ограничения

1. Датасет узкий: 373 кадра двух зон одного полигона, эвристические метки и
   визуальные исправления агента. Перед соревнованием нужна независимая
   ручная проверка всех рамок и новая съёмка с камер робота (расстояния,
   ракурсы, встречный свет, смаз, частичные перекрытия, пустые кадры).
2. Несколько горящих секций — неоднозначное табло. Это generic/unknown
   (или red при включённом приоритете), не разрешающий green. `counts`
   содержит все три цвета, но не заменяет подтверждение цветовой головы YOLO.
3. Проекция знаков на поле и в 3D — оценка по высоте рамки и геометрии C930e,
   не измерение дальности Kinect. Не используйте её как единственный источник
   для торможения. Масштаб 1:1 честный ровно настолько, насколько совпадают
   физические размеры в `CLASS_INFO` с макетами на полигоне.
4. Сервис не включает тягу и не снимает E-STOP. Интеграция с навигацией —
   следующий шаг: `road_traffic.py` уже умеет стоп-линии и циклы светофора,
   к нему можно подвести `trafficLight.state` вместо симуляции по времени.
5. На 2-ядерном CPU дообучение занимает десятки минут; GPU в этой среде нет.
   Встроенный детектор работает без PyTorch и без весов, но уступает YOLO в
   устойчивости к ракурсам и частичным перекрытиям.
6. Глубина Kinect пока не уточняет координаты знаков: 3D-обзор показывает
   `positionSource: "camera-estimate"`. Для метровой привязки к облаку точек
   нужна совместная калибровка камер и Kinect.
