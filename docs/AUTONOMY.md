# Автономное движение и построение карты (4 × C930e + Kinect 360 + лидар)

Робот сам объезжает помещение и достраивает карту: ищет границу неизведанного,
строит безопасный маршрут по существующему планировщику, едет, обновляет
occupancy grid, сохраняет карту и повторяет. Это **не Nav2 и не сертифицированная
система безопасности** — это осторожный режим поверх уже существующей
навигации `robot_control/navigation.py`.

## Что откуда берётся

| Сенсор | Роль | Куда идёт |
|---|---|---|
| **Лидар 360°** (RPLIDAR/LD06/LDS-01/ROS 2) | основной источник карты и позы | `SlamMapService.ingest()` + scan matching, `NavigationService._preflight` |
| **Kinect 360** (спереди по центру) | глубина, ближняя зона и препятствия впереди | `POST /api/kinect/depth` → `kinect.depth_to_scan()` → `SlamMapService.ingest_kinect()` в **ту же** сетку |
| **4 × Logitech C930e** (FL, FR спереди; RL, RR сзади по бокам) | круговой обзор и визуальные ориентиры | MJPEG `/api/camera/<0…3>/frame`, кадры с привязкой к позе в `data/landmarks/` |
| Одометрия/телеметрия колёс | подтверждение готовности тяги и остановки | существующий `MasterBridge`/`NavigationService` |

Kinect **не** участвует в оценке позы и не подменяет «свежесть» лидара: позу
по-прежнему определяет 360° скан. Поэтому неоткалиброванный Kinect не может
«сдвинуть» локализацию, а навигация не поедет, если лидар пропал.

## 1. Физическое подключение

* 4 камеры C930e — в четыре USB-порта с отдельным питанием (хаб с внешним
  питанием обязателен: 4 камеры + 4 Arduino + лидар + Kinect).
* Kinect 360 — один штатный USB-разъём адаптера и отдельный блок питания. В USB-списке `NUI Camera` — интерфейс изображения/глубины, который надо выбирать в карточке Kinect; `NUI Audio` — микрофонный интерфейс того же сенсора, не источник глубины и для Kinect-порта не выбирается. Не подключайте их как два отдельных сенсора. Глубина работает через `libfreenect`, `OpenNI2` или ROS 2.
* `RC_KINECT_PORT` из вкладки «Устройства» сопоставляется с индексом libfreenect через USB-топологию PyUSB/libusb; в статусе показывается `capturePort`. Для физической привязки нужен именно `freenect` + `pyusb`; OpenNI2/ROS 2 сейчас не запускаются с выбранным портом, чтобы не отдавать кадры от другого устройства. Один передний Kinect поддерживается; второй не включать.
* Лидар 360° как обычно, см. [connections.md](connections.md) и
  [ROS2_LIDAR.md](ROS2_LIDAR.md).

Порты камер закрепите стабильными путями `/dev/v4l/by-id/…` — иначе после
перезагрузки `video0…video3` перепутаются. Назначить порты можно на бортовом
экране: свайп «Камеры» → «Настройка камер» (без PIN), либо прямо в `.env`:

```ini
RC_CAMERA_FRONT=/dev/v4l/by-id/…FL…-video-index0
RC_CAMERA_REAR=/dev/v4l/by-id/…RL…-video-index0
RC_CAMERA_FRONT_RIGHT=/dev/v4l/by-id/…FR…-video-index0
RC_CAMERA_REAR_RIGHT=/dev/v4l/by-id/…RR…-video-index0
```

## 2. Геометрия: что нужно замерить

Ось **X — вперёд**, **Y — влево**, начало координат — центр корпуса (как на
карте лидара). `yaw=0` — камера смотрит вперёд, `+90°` — влево, `180°` — назад.
По вашим эскизам передняя пара сходится под ~50°, задняя под ~90°. Шаблон в
`.env.example` повторяет это грубо, но **обязательно замерьте** и впишите:

```ini
RC_CAMERA_FL_X_M=0.30
RC_CAMERA_FL_Y_M=0.25
RC_CAMERA_FL_Z_M=0.28
RC_CAMERA_FL_YAW_DEG=-25
... остальные три камеры ...
RC_KINECT_X_M=0.35
RC_KINECT_Y_M=0.0
RC_KINECT_Z_M=0.45
RC_KINECT_YAW_DEG=0
RC_KINECT_PITCH_DEG=0
```

Вносить замеры можно не только руками: на `/map` и `/route` откройте
**«Калибровка геометрии»** — там все 38 полей на одном экране (4 камеры × 5 +
Kinect × 13 + тяга и скорость × 5) с текущими значениями, диапазонами и
подсказками. «Сохранить в .env» пишет только известные ключи атомарно, не
трогая остальные строки файла, и сразу применяет их к процессу. На пульте
8080 сохранение дополнительно защищено CSRF-токеном и заголовком
`X-Robot-Control: calibration`.

**Скорость не угадывают.** `RC_NAV_MPS_PER_PERCENT` в шаблоне пуст, в форме
оно показано пустым с подсказкой «измерить на площадке», а пустая строка при
сохранении отклоняется — иначе навигация отказала бы уже после нажатия
«Начать». Замерьте проезд на площадке и запишите результат:

```bash
# робот проехал 2 м за 8 с при тяге 4%
.venv/bin/python scripts/measure_nav_speed.py --distance 2 --seconds 8 --percent 4
# → RC_NAV_MPS_PER_PERCENT=0.0625
.venv/bin/python scripts/measure_nav_speed.py --distance 2 --seconds 8 --percent 4 --save-env
```

Скрипт ничего не запускает и не двигает робот: он только считает по вашим
замерам и (с `--save-env`) атомарно дописывает ключ в `.env`. Остальные поля
группы — `RC_NAV_SPEED_MPS`, `RC_NAV_MAX_PERCENT`, `RC_NAV_FOOTPRINT_M`,
`RC_LIDAR_OFFSET_M` — тоже лежат в той же форме.

Пока заданы не все углы, `GET /api/sensors/layout` возвращает
`calibrated: false`, а панель обследования показывает предупреждение; карта
при этом всё ещё строится лидаром, но не стоит рассчитывать на точные углы
обзора. C930e по умолчанию: 82° по горизонтали, 52° по вертикали; Kinect 360:
57° × 43°, 0,45…4 м.

Проверить геометрию и отсутствие дублей портов:

```bash
curl http://127.0.0.1:8090/api/sensors/layout | python3 -m json.tool
curl http://127.0.0.1:8090/api/cameras | python3 -m json.tool
```

## 3. Запуск Kinect

На борту, вместе с киоском (8090), публикатор запускается отдельным процессом.
Он читает `RC_KINECT_PORT` из `.env` и передаёт libfreenect индекс именно
выбранного NUI Camera; если порт не найден или драйвер не может сопоставить
топологию, процесс откажется запускать чужое устройство.

```bash
# выбрать NUI Camera во вкладке /devices, затем установить libfreenect + pyusb
# после изменения выбора перезапустить: sudo systemctl restart robot-kinect-depth
./scripts/kinect_depth.sh --list-backends

# проверить весь API/карту без оборудования (это НЕ тест датчика)
.venv/bin/python scripts/kinect_depth_publisher.py --source demo --once

# запуск с сохранённой RC_KINECT_PORT; предпочтительно через wrapper
./scripts/kinect_depth.sh --foreground
```

Публикатор уменьшает кадр до 160×120 и шлёт `uint16` (мм) в
`POST /api/kinect/depth` с заголовком `X-Robot-Control: kinect`. Сервер сам
переводит глубину в полярные лучи, отбрасывает пол/потолок
(`RC_KINECT_MIN_HEIGHT_M`…`MAX_HEIGHT_M`) и вписывает их в карту.

### 3D-просмотр на главном экране

В правой панели доступны **Лидар · 2D**, **Kinect · 3D** и **Общий обзор · 3D**.
Общий обзор накладывает свежий скан лидара и последний кадр глубины в одной
системе координат робота: плоскость лидара расположена на высоте 550 мм,
Kinect — на 130 мм впереди него; высота и наклон Kinect берутся из его текущей
конфигурации (`RC_KINECT_Z_M`, `RC_KINECT_YAW_DEG`, `RC_KINECT_PITCH_DEG`).
Оранжевые точки — лидар, сине-зелёные — Kinect. Вид вращается перетаскиванием,
масштабируется колесом/щипком и кнопками `−`, `+`; `⊙` сбрасывает ракурс.

Это **только live-отображение** двух последних источников: облако не накапливается,
не записывается в карту и не сохраняется. Просмотр не предназначен для
навигации или оценки свободного пространства; отсутствие глубины не доказывает,
что препятствия нет. Старые данные автоматически исчезают. Плоский вход `points`
или `ranges` недостаточен для Kinect 3D — нужен свежий сырой `depth`.

3D-просмотр использует работающий публикатор робота и не запускает параллельно
Depth Studio или второй USB-драйвер. TSDF/ICP, накопление проходов и экспорт из
Depth Studio здесь **не интегрированы**. Геометрия приблизительная, цвет точек
условный (по дальности), не RGB. Данные для просмотра ограничены 160×120;
это не меняет построение карты лидаром или управление роботом.

Для libfreenect сырой 11-битный кадр теперь преобразуется в миллиметры по
приближённой формуле Kinect v1 до отправки: это меняет и 2D-псевдоскан Kinect,
используемый картой. Проверьте дистанцию до объектов на физическом оборудовании
и калибровку до использования данных; на физическом датчике изменение не
проверено. При отсутствии кадра проверьте питание, публикатор и `/api/kinect/status`.

Проверка:

```bash
curl http://127.0.0.1:8090/api/kinect/status   # connected, frames, points
curl http://127.0.0.1:8090/api/kiosk_map       # kinectScans, kinectPoints
```

`freenect` и `pyusb` намеренно **не** добавлены в основной `requirements.txt`:
им нужны системные библиотеки. Команды установки — в `requirements-kinect.txt`.
Хотя status перечисляет OpenNI2/ROS 2 как установленные драйверы, с выбранным
`RC_KINECT_PORT` publisher разрешает только `freenect`: прочие backends пока не
умеют гарантировать соответствие USB-топологии. `/api/kinect/status` показывает
`captureSource` и `capturePort` реально поступившего кадра.

**Автозапуск уже настроен.** `scripts/start_robot.sh` после ответа киоска 8090
поднимает `scripts/kinect_depth.sh` (по умолчанию
`RC_KINECT_PUBLISHER_AUTOSTART=1`, отключается значением `0`), а
`scripts/install_ubuntu.sh` вместе с `--autostart` ставит юнит
`robot-kinect-depth.service`. `scripts/autostart.sh` и `scripts/stop.sh`
умеют показывать, включать, выключать и гасить его наравне с киоском.

```bash
./scripts/kinect_depth.sh --list-backends   # что реально установлено
./scripts/kinect_depth.sh --foreground      # для systemd / отладки
./scripts/stop.sh                           # гасит и публикатор тоже
```

Важно: обёртка запускает публикатор строго с `--source auto` и **никогда не
подменяет отсутствующий драйвер демо-кадром**. Без физического Kinect она
завершится с подсказкой про `requirements-kinect.txt`, а панель так и покажет
«Нет свежего кадра Kinect 360» — свежий демо-кадр не должен создавать иллюзию
готовности к выезду.

## 4. Включение автообследования

```ini
RC_NAV_ENABLE=1          # существующая осторожная навигация
RC_EXPLORE_ENABLE=1      # сам цикл обследования
```

Затем на странице **«Карта лидара»** (или **«Движение по маршруту»**) в панели
**«Автообследование»**:

1. Убедитесь, что лидар и Kinect дают свежие данные (индикаторы в панели).
2. Осмотрите ближнюю зону вокруг робота и поставьте галочку подтверждения —
   это аналог проверки слепой зоны лидара у обычного маршрута.
3. Нажмите **«Начать обследование»**. Дальше робот едет сам: выбирает границу
   UNKNOWN-области, строит маршрут, едет, сохраняет PGM/PNG/ YAML карту и
   снимает кадры с четырёх камер.
4. **«Стоп»** или **E-STOP** мгновенно снимает тягу и завершает цикл.

То же через API (борт, 8090):

```bash
curl -H 'X-Robot-Control: exploration' -H 'Content-Type: application/json' \
  -d '{"blindZoneChecked":true}' http://127.0.0.1:8090/api/exploration/start
curl http://127.0.0.1:8090/api/exploration/status
curl -H 'X-Robot-Control: exploration' -X POST http://127.0.0.1:8090/api/exploration/stop
```

На пульте 8080 те же маршруты доступны после входа оператора и требуют
CSRF-токен (берётся из `/api/exploration/status`), команды проксируются на борт.

## 5. Ограничения и безопасность

* **Выключено по умолчанию.** Нужны `RC_NAV_ENABLE=1` и `RC_EXPLORE_ENABLE=1`,
  свежий скан лидара, качество scan matching, готовность тяги и отсутствие
  E-STOP. Любая потеря Kinect во время движения останавливает обследование.
* Цикл завершается по: пределу шагов (`RC_EXPLORE_MAX_STEPS`), времени,
  отсутствию новых границ, многократному отсутствию прироста карты, E-STOP,
  кнопке «Стоп», ошибке планировщика или таймауту поездки.
* Шасси **не умеет разворот на месте**: доступны прямые/крабовые отрезки
  в пределах ±28°, поэтому кластеры границ позади робота имеют низкий приоритет.
* Скорость — как у обычной навигации (`RC_NAV_SPEED_MPS`, по умолчанию 0,05 м/с),
  предел тяги `RC_NAV_MAX_PERCENT`. Все проверки `_preflight`, watchdog 650 мс,
  `X-Robot-Control`, CSRF и общая защёлка E-STOP сохранены.
* Ближняя слепая зона лидара (радиус `min_range` карты) остаётся единственным
  местом, где требуется человек: Kinect смотрит вперёд, сзади его нет, поэтому
  оператор подтверждает осмотр перед пуском. Не снимайте эту галочку
  (`RC_EXPLORE_REQUIRE_BLIND_CHECK=0`) без дополнительных датчиков сзади.
* **Не публикуйте 8080/8090 в интернет.** Держите доступным физический
  аварийный выключатель, первые прогоны — на вывешенных колёсах.
* Kinect v1 не видит солнечный свет, чёрные/глянцевые поверхности и стекло;
  лидар остаётся основным датчиком. Низкие препятствия (< `MIN_HEIGHT_M`) и
  объекты вне 57° спереди глубиной не увидятся — для них работают лидар и
  камеры оператора.

## 6. Визуальные ориентиры

На каждом шаге (отъезд и прибытие) `LandmarkRecorder` сохраняет по свежему
кадру с каждой из четырёх камер в `data/landmarks/` (каталог в `.gitignore`)
и дописывает `index.json` с позой, целью и ролью камеры. Посмотреть:

```bash
curl 'http://127.0.0.1:8090/api/exploration/landmarks?limit=5'
# кадры: /api/exploration/landmark/step003-cam2.jpg
curl -H 'X-Robot-Control: exploration' -X POST \
  http://127.0.0.1:8090/api/exploration/landmarks/clear
```

Это **привязанные к позе снимки**, а не визуальный SLAM: полноценный RTAB-Map /
ORB-SLAM3 требует калибровки каждой камеры, ROS 2 и отдельного стека. Карта
здесь строится лидаром + глубиной Kinect.

## 7. Диагностика

| Признак | Что проверить |
|---|---|
| «Автообследование выключено» | `RC_EXPLORE_ENABLE=1`, перезапуск процессов |
| «Сначала включите навигацию» | `RC_NAV_ENABLE=1` и готовность `GET /api/navigation/status` |
| «Нет свежего кадра Kinect» | публикатор запущен, `/api/kinect/status`, USB-питание Kinect |
| «Новых границ нет» | карта уже построена или сетка не обновляется; `/api/kiosk_map` → `scans`, `quality` |
| «Карта перестала расти» | лидар/поза стоят на месте; проверьте `matched`, `quality`, `RC_NAV_QUALITY_MIN` |
| Камеры перепутаны | закрепите `/dev/v4l/by-id/…` в «Настройке камер» |
| `duplicatePorts` в `/api/sensors/layout` | два разных `RC_CAMERA_*` указывают на один порт |
| «Поездка превысила таймаут» | `RC_EXPLORE_STEP_TIMEOUT_S`, связь с шасси, застрявшее колесо |

## 8. Чек-лист готовности перед пуском

`/api/exploration/status` содержит `blockers` (то, что реально не даст
запуститься), `warnings` (что стоит проверить), `navigation` (полная диагностика
тяги) и `canStart`. Панель показывает их списком и держит кнопку «Начать»
выключенной, пока есть blockers.

`navigation.checks` — это те же 14 проверок, что `NavigationService` делает
перед каждой поездкой: `enabled`, `speedCalibrated`, `speedWithinLimit`,
`masterReady`, `driveStopped`, `mapFresh`, `mapReady`, `mapTrusted`,
`mapIntegrity`, `scanReady`, `poseReady`, `mapDecayDisabled`,
`footprintSufficient`, `estopClear`. Блок **«Готовность навигации»** на `/map` и
`/route` рисует их все со статусом ✅/⚠ ещё до пуска; `navigation.errors`
содержит human-readable названия невыполненных, а когда навигация уже включена,
они дополнительно попадают в `blockers` с префиксом «Навигация:». Раньше
оператор видел только первую причину (`RC_NAV_ENABLE`) и узнавал про пустой
`RC_NAV_MPS_PER_PERCENT` уже по отказу планировщика.

```bash
# полный ответ, включая navigation.checks
curl http://127.0.0.1:8090/api/exploration/status | python3 -m json.tool
# только «готов / что не так»
curl http://127.0.0.1:8090/api/exploration/status | python3 -c \
  'import json,sys; n=json.load(sys.stdin)["navigation"]; print(n["ready"], n["errors"])'
```

| Поле | Источник |
|---|---|
| `RC_EXPLORE_ENABLE=1`, `RC_NAV_ENABLE=1` | иначе режим и навигация выключены |
| E-STOP снят | `robot_control/estop.py` |
| свежий кадр Kinect | `RC_EXPLORE_REQUIRE_DEPTH`, `/api/kinect/status` |
| галка «Ближняя зона осмотрена» | физический осмотр оператором, не показание датчика |
| все углы внесены | «Калибровка геометрии», `/api/sensors/layout → calibrated` |
| карта не пуста, лидар свежий | `/api/kiosk_map → scans, quality, trusted` |
| замеренная скорость, шасси, footprint, pose/scan | `/api/exploration/status → navigation.checks` (14 проверок) |

Предупреждения не блокируют пуск: например, без калибровки робот поедет, но
лучи Kinect будут смещены относительно реального монтажа.

## 9. Сухой прогон без железа

Полный цикл можно проверить на синтетической карте — без лидара, шасси и
Kinect. Скрипт повторяет выбор границы, «поездку», рост карты, автосохранение
и запись ориентиров:

```bash
.venv/bin/python scripts/explore_sim.py            # отчёт
.venv/bin/python scripts/explore_sim.py --steps 8 --json
```

Отчёт `ok: true` означает только исправность логики, **не** безопасность
движения: физические проверки из `docs/navigation.md` остаются обязательными.

## 10. Второй Kinect 360 сзади (пока не поддержан publisher-ом)

API и геометрия умеют хранить отдельную конфигурацию `rear`, но отдельная
привязка второго экземпляра не реализована. Publisher сейчас разрешает только
передний NUI Camera из `RC_KINECT_PORT` и откажется публиковать `rear`; **не
подключайте второй Kinect и не включайте `RC_KINECT_REAR_ENABLE`** до отдельной
реализации и аппаратной проверки.

## 11. Проверки интерфейса без браузера

Логику панели обследования и формы калибровки проверяют Node/`vm`-тесты
(как остальные экранные скрипты проекта), без Chromium:

```bash
node tests/js/explore_screen.js
.venv/bin/python -m pytest -q tests/test_explore_screen.py tests/test_calibration.py
```

Это проверка DOM-логики и заголовков запросов, а не замена просмотру страницы
в реальном браузере на роботе.
